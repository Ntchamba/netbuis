# T041b — La recherche trouve un commerce par son nom (D-27)

## Ce qui a changé
- `BusinessProfile.normalized_name` (non éditable) = `normalize_text(name)`, recalculé dans `save()` (y compris `save(update_fields=["name"])`). Migration `business/0005_nom_normalise` : ajout du champ, remplissage des lignes existantes (RunPython), index GIN `business_profile_name_trgm` (`gin_trgm_ops`). Un index sur `unaccent(lower(name))` est impossible (`unaccent` n'est pas IMMUTABLE).
- `search_service._profile_field_scores` : colonne `s_name` (poids `WEIGHT_NAME = 0,95`) dans la requête qui lit déjà secteur et catégorie de service : aucune requête de plus.
- Seuls les profils de `BusinessProfile.objects.visible()` peuvent sortir (inchangé). Contrat d'API inchangé (`openapi.yaml` identique à la génération).

## Ordre de pertinence (documenté dans `search_service.py`, testé : `test_08`)
offre exacte / produit (1,0) > **nom du commerce (0,95)** > sous-catégorie, catégorie de service (0,9) > secteur (0,7).
Rappel : le classement final reste « abonnés d'abord, palier de pertinence (4 paliers), proximité, score fin ». 0,95 et 0,9 sont dans le même palier : la différence joue après la proximité.

## Mesures (5 000 commerces fictifs, 3 599 visibles, 30 requêtes, `search()` + chargement de 20 profils)
| Requête | médiane | p95 | max |
|---|---|---|---|
| mot du nom (« [DÉMO] » et mots communs : 3 599 résultats, pire cas) | 139 ms | 198 ms | 275 ms |
| nom complet | 135 ms | 162 ms | 185 ms |
| mot du nom avec faute | 128 ms | 169 ms | 183 ms |
| produit (référence) | 70 ms | 86 ms | 97 ms |

Tout est sous 300 ms (`logs/T041b-perf.txt`).

## Plan d'exécution (`logs/T041b-explain.txt`)
- `WHERE normalized_name %> 'baobab'` : Seq Scan, 19,7 ms (le planificateur préfère le balayage sur 5 000 lignes).
- Même requête avec `enable_seqscan = off` : `Bitmap Index Scan on business_profile_name_trgm`, 2,8 ms. L'index est donc utilisable (test `test_14`).
- À noter : la recherche calcule `word_similarity()` sur chaque ligne (comme pour les produits), ce qui n'emploie pas l'index ; il servira si on filtre avec l'opérateur `%>` sur de très grosses tables.
