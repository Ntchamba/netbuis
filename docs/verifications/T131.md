## Mesures de latence (D-26)
Définition : temps entre l'envoi de `POST /api/calls/sessions/` et la réception de l'événement `ringing` par le **dernier** des 3 flux agent déjà connectés (valeur la plus défavorable). Un appelant différent par appel.

| Essai | p50 | moyenne | p95 | max |
|---|---|---|---|---|
| Test automatisé, suite complète (client Django en mémoire, vraie base, vrai LISTEN/NOTIFY, vrai flux SSE) | 39,7 ms | 40,1 ms | **46,8 ms** | 60,2 ms |
| Même test, deux autres exécutions | 39,1 / 36,5 ms | 41,0 / 39,2 ms | 55,4 / 46,7 ms | 94,4 / 246,5 ms |
| **Serveur réel `uvicorn 0.54.0`, HTTP réel en boucle locale** (script ponctuel, 100 appels, 3 flux agent) | 43,3 ms | 43,4 ms | **51,8 ms** | 65,6 ms |

Cible serveur : p95 < 250 ms → atteinte (≈ 5 fois de marge). Le maximum de 246,5 ms a été vu une fois pendant la suite complète (machine chargée) : il reste sous la cible, mais le test ne regarde que le p95.
Hors mesure (non mesurable ici) : réseau mobile 3G/4G de l'appelant, négociation WebRTC Jitsi, serveur Jitsi réel.

Essai avec un vrai serveur ASGI : base jetable, `uvicorn config.asgi:application`, 3 agents ouverts en SSE, 100 appelants ; à la fermeture des clients, `open_streams` est revenu à 0 pour les 3 agents (la déconnexion libère bien la connexion LISTEN et la présence) ; `expire_calls` a ensuite fermé les 100 sonneries restées sans réponse (`missed / timeout`). La base jetable a été supprimée.

## Décisions prises
1. **WhatsApp** : `initiate` portait aussi WhatsApp (`channel=whatsapp`). Pour que « WhatsApp inchangé » reste vrai, le lien est servi par `POST /api/calls/whatsapp/` `{business_id, platform}` → `{call_id, wa_url}` (mêmes contrôles, mêmes codes d'erreur en majuscules, même limite, même journal `CallLog`). Le numéro y reste dans `wa_url` (inévitable pour `wa.me`). Le mobile (T133) doit appeler cette route.
2. **Droit** : le droit vit dans `apps/admin_panel/services/rights_service.py` (pas `accounts`) : constante `REPONDRE_APPELS`, libellé, ajouté à « Validateur » (« Administrateur complet » reçoit toutes les permissions du dictionnaire). Migration `admin_panel/0008_repondre_aux_appels` (options du modèle + données).
3. **Audit** : `AuditLog.action` est une liste fermée de `admin_panel` (ajouter une action = migration hors périmètre). Les réponses et refus sont donc tracés dans les tables de l'appli appels (`CallSession.agent/answered_at`, `CallSessionDecline`).
4. **États** : tous les agents disponibles ont refusé → `declined` (motif `all_declined`) ; sonnerie dépassée → `missed` (motif `timeout`). Le filtre de la liste admin « manqués » est `state=missed,declined`.
5. **Présence** : `AgentPresence.available` vaut `false` à la création : l'agent doit choisir « Disponible » (le flux annonce son état par l'événement `presence`). Disponible = choix + flux ouvert + activité < 25 s + droit relu en base.
6. **Codes d'erreur** : les nouveaux codes sont en minuscules (`call_already_active`, `call_taken`, `call_not_ringing`, `call_not_answered`, `jitsi_not_configured`, `no_agent_available`), comme tout `/api/admin/` ; les codes hérités de la liste fermée d'appel restent en majuscules (`RATE_LIMITED`, `BUSINESS_NOT_ACTIVE`…, `ACCOUNT_BLOCKED` pour WhatsApp). `POST /api/calls/sessions/` utilise la permission par défaut du projet : compte bloqué → 403 `account_blocked`.
7. **Sans agent** : réponse 200 `{state: "unavailable", code: "no_agent_available", jitsi: null, ring_seconds: 0}` ; la session est créée (état `unavailable`) et compte dans les limites.
8. **Historique** : `GET /api/calls/history/` fusionne sessions (`type: "call"`, `session_id`, `state`, `id: null`) et liens WhatsApp / anciens appels (`id` = journal, `session_id: null`) ; 200 lignes par source au plus. Le retour d'appel (`/api/calls/<int>/feedback/`) ne concerne plus que le journal WhatsApp / anciens appels.
9. **Dépendance** : `uvicorn==0.54.0` ajouté à `requirements/base.txt` (aucun serveur ASGI n'était installé). `PyJWT` (jeton HS256) était déjà installé via simplejwt.
10. **Fichiers hors périmètre modifiés (conséquences directes)** : `apps/admin_panel/{services/rights_service.py, migrations/0008…, tests/_contrat.py, tests/test_contrat.py, tests/test_permissions.py, tests/test_accounts.py}` ; `backend/tests/{test_security_routes.py, test_security_phone_leak.py, test_security_logs.py, e2e/test_flow_search_call.py}` ; `backend/.env.example` (noms des variables Jitsi).
11. **Tests `transaction=True`** : ils vident la base, donc aussi les groupes posés par les migrations ; la fixture `admin_groups` (`apps/calls/tests/conftest.py`) rejoue les fonctions des migrations 0002 et 0008 si le droit a disparu (`serialized_rollback` échoue quand un test d'une autre appli a déjà vidé la base).

## Limites connues / à décider
- **JaaS** : jeton HS256 seulement (Jitsi auto-hébergé). D'après sa documentation, JaaS signe en RS256 avec `kid` : non implémenté (question Q1 / D-28).
- Les champs de jeton Jitsi (`context.user.moderator`, `features`) suivent le format usuel du module `token` de Prosody ; à confirmer sur le vrai serveur (essai réel : T135).
- Les statistiques du dashboard (`stats_service`, `analytics_service`), `calls_count` des commerces et les tendances lisent encore `CallLog` : les appels à l'équipe n'y sont pas comptés. À traiter dans une tâche dédiée (hors périmètre de T131).
- Le filtre de journaux `PersonalDataFilter` masque des morceaux d'identifiant de session (suites de 6 chiffres) dans les lignes de journal ; inoffensif mais déroutant.
