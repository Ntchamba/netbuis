Chaque agent (A, B, C) a trois sous-agents et un tableau par sous-agent : les fichiers à toucher, la fonctionnalité à écrire et les méthodes conseillées. Le squelette du dépôt existe déjà : on remplit les fichiers, on n'en invente pas d'autres.

## Comment lire ce cahier

| Colonne | Sens |
| --- | --- |
| N° | `A1.4` = agent A, sous-agent 1, tâche 4 |
| Fichiers à toucher | Chemins relatifs au dossier indiqué en tête de chaque tableau. Un agent ne modifie rien d'autre. |
| Ce qu'il faut implémenter | Le comportement attendu, en termes précis (routes, champs, règles, textes, design). Le reste se déduit du projet. |
| Méthodes conseillées | Bibliothèques, classes ou fonctions à utiliser. Ce sont des propositions : un agent peut choisir mieux s'il le justifie dans sa PR. |
| Étape · plan | Étape d'exécution (É1 à É8, voir la dernière section) et numéro de la tâche dans le plan de la semaine (`A.6`, `B.12`…) quand elle existe. « nouveau » = absent du plan de 97 tâches. |

## Règles communes

1. Un dossier a un seul propriétaire. Besoin d'un changement ailleurs : le noter dans la PR pour l'orchestrateur.
2. Le contrat `docs/api/openapi.yaml` fait foi. Le mobile et le dashboard codent d'abord contre des données factices (`USE_FAKE_API`, `VITE_USE_MOCKS`).
3. Zones sensibles, relues ligne par ligne par Jeff : OTP et jetons, connexion admin, appel, tout `payments/`.
4. Aucune clé, aucun mot de passe, aucun jeton dans le code, les tests ou les logs.
5. Une tâche est terminée quand ses tests passent, que `openapi.yaml` est à jour et qu'aucun fichier hors liste n'a été ajouté.
6. Hors de ce cahier, car reportés : déploiement Railway et Vercel, inscription et configuration CamPay réelles.
